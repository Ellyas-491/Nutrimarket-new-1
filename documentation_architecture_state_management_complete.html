1.0 Pendahuluan & Dekomposisi Tiga Lapis Arsitektur

Arsitektur aplikasi NutriMarket dirancang dengan mematuhi prinsip Separation of Concerns (SoC) dan Single Responsibility Principle (SRP). Kode dibagi secara modular ke dalam 3 (tiga) tingkatan independen:

1.1 Presentation Layer (Lapisan Presentasi / UI)

Direktori: lib/features/*/screens/ dan lib/features/*/widgets/
Peran: Bertanggung jawab penuh atas penampilan antarmuka visual, rendering tata letak, komponen formulir, animasi transisi, dan visualisasi kondisi status. Layar tidak memuat logika bisnis langsung; setiap aksi pengguna (misal: penekanan tombol) didelegasikan langsung ke lapisan domain.

1.2 Domain / Business Logic Layer (Lapisan Logika Bisnis)

Direktori: lib/features/*/services/ dan product_repository.dart
Peran: Merupakan inti dari aturan bisnis sistem. Mengatur mutasi state, validasi kuota pesanan, perhitungan diskon kupon, filter nutrisi, sinkronisasi offline-first, dan interaksi AI Assistant. Mewarisi ChangeNotifier untuk memicu pembaruan antarmuka via notifyListeners().

1.3 Data Layer (Lapisan Akses Data & Penyimpanan)

Direktori: lib/data/remote/, lib/data/local/, dan lib/features/*/models/
Peran: Menangani pertukaran data mentah. Mengelola API Supabase (PostgreSQL & Auth), enkripsi data sensitif (FlutterSecureStorage), penyimpanan cache lokal (SharedPreferences), serta serialisasi JSON/Map ke objek model Dart.

2.0 Pola Manajemen State Berbasis Provider & ChangeNotifier

2.1 Definisi & Manfaat Pola Provider

Dalam arsitektur Flutter, Provider bertindak sebagai lapisan perekat antara Domain Layer dan Presentation Layer. Provider mengimplementasikan pola Observer, di mana State Holder bertindak sebagai Subject dan Widget bertindak sebagai Observer.

Keunggulan Arsitektur: Menghilangkan kebutuhan prop drilling (pengoperan parameter berlapis antar widget), meminimalkan konsumsi memori dengan hanya me-rebuild sub-tree widget yang terdampak, serta menyederhanakan pengujian unit terisolasi (isolated unit testing).

2.2 Registrasi Sentral MultiProvider pada Root Aplikasi

Seluruh penyedia status diinisialisasi pada tingkat tertinggi pohon widget (root) di file lib/main.dart (baris 67–78), memastikan ketersediaan akses status secara global di seluruh rute layar: 

// lib/main.dart
class HealthCarePlusApp extends StatelessWidget {
  const HealthCarePlusApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MultiProvider(
      providers: [
        ChangeNotifierProvider<SupabaseService>.value(value: SupabaseService()),
        ChangeNotifierProvider<SecureStorageService>.value(value: SecureStorageService()),
        ChangeNotifierProvider<OfflineSyncService>.value(value: OfflineSyncService()),
        ChangeNotifierProvider<ProductRepository>.value(value: ProductRepository()),
        ChangeNotifierProvider<HistoryService>.value(value: HistoryService()),
        ChangeNotifierProvider<CartService>.value(value: CartService()),
        ChangeNotifierProvider<OrderService>.value(value: OrderService()),
        ChangeNotifierProvider<FavoriteService>.value(value: FavoriteService()),
        ChangeNotifierProvider<NotificationService>.value(value: NotificationService()),
      ],
      child: const MaterialApp(home: SplashScreen()),
    );
  }
}

2.3 Resolusi Context: Watch, Read, dan Consumer

Sintaks Pemanggilan Karakteristik Eksekusi Skenario Penggunaan yang Tepat
context.watch<T>() Mendaftarkan widget sebagai pendengar aktif. Widget akan me-rebuild otomatis saat state berubah. Merender teks dinamis, jumlah badge keranjang, dan list data produk.
context.read<T>() Mengambil referensi instance service tanpa mendaftarkan widget sebagai pendengar (no rebuild). Didalam fungsi callback onPressed, trigger tombol login, atau aksi klik.
Consumer<T> Membatasi area rebuild hanya pada closure builder internal widget tertentu. Optimasi performa pada pohon widget yang kompleks dan berukuran besar.

3.0 Matriks Siklus Status Antarmuka Pengguna (UI State Lifecycle)

3.1 Taksonomi 5 Kondisi State Deterministik

Setiap antarmuka fungsional pada aplikasi NutriMarket menangani 5 kondisi status diskrit untuk menjamin keterandalan interaksi pengguna:

State Indikasi Sistem Manifestasi Visual UI Penanganan Teknis
1. INITIAL Kondisi awal saat widget dipasang pertama kali pada tree. Form input kosong, status placeholder netral. Inisialisasi controller, muat data awal dari cache lokal via initState().
2. LOADING Proses asinkron sedang berjalan (Network I/O atau Database fetch). CircularProgressIndicator atau Skeleton Loading. Blokir interaksi duplikat dengan menonaktifkan tombol submit selama `isLoading == true`.
3. EMPTY Operasi fetch berhasil dieksekusi, namun himpunan data bernilai 0. Ilustrasi grafis, pesan ramah, dan tombol aksi bantuan. Percabangan if (items.isEmpty) mengalihkan render ke widget informasi kosong.
4. SUCCESS Operasi komputasi/fetch data selesai dengan status valid. Rendering daftar kartu (Card Grid), Toast hijau, dialog sukses. Pembaruan model lokal, navigasi halaman otomatis, atau reset status form.
5. ERROR Terjadi kegagalan jaringan, timeout, atau exception kredensial. Toast merah (AppToast), indikator status gagal, tombol Coba Lagi. Blok try-catch menangkap exception, memetakan ke pesan ramah, dan memulihkan state.

3.2 Alur Pemulihan Kesalahan (Error Recovery Flow)

Aplikasi mengadopsi strategi Graceful Degradation dan Offline Fallback: ketika komunikasi jaringan ke Supabase Cloud gagal, sistem tidak melakukan crash, melainkan secara mulus memuat data dari Local Storage cache dan menampilkan notifikasi peringatan non-intrusif kepada pengguna.

4.0 Spesifikasi Teknis Katalog Service & Repository

Berikut adalah spesifikasi teknis lengkap dari 9 komponen pengelola status yang terdapat di dalam sistem:

Komponen Lokasi File State Utama yang Dikelola Integrasi Data Layer
ProductRepository lib/features/products/services/ _products, _isLoading, kategori filter. SharedPreferences (Local cache) & Supabase REST API.
CartService lib/features/cart/services/ _items, itemCount, subtotal, total. Local Storage persistence & Supabase user cart sync.
OrderService lib/features/orders/services/ _orders, activeOrders, completedOrders. Penyimpanan riwayat transaksi offline & Supabase cloud orders.
FavoriteService lib/features/products/services/ _favoriteIds, status wishlist. Local cache wishlist & Supabase favorites table.
HistoryService lib/features/orders/services/ userProfile, riwayat AI Chat. Secure storage data profil & Supabase chat sessions.
SupabaseService lib/data/remote/ currentUser, status login, token sesi. PostgreSQL Cloud, Supabase GoTrue Auth API.
OfflineSyncService lib/data/local/ Antrean sync transaksi offline. ConnectivityPlus & Local sync queue dispatcher.
SecureStorageService lib/data/local/ Auth token, user credential terenkripsi. Android Keystore / EncryptedSharedPreferences.
NotificationService lib/features/notifications/services/ _notifications, status unread. FlutterLocalNotificationsPlugin sistem OS.

5.0 Studi Kasus Implementasi Kode Sumber Nyata

5.1 Implementasi Reaktif Katalog Produk (HomeScreen)

Potongan kode dari lib/features/products/screens/home_screen.dart (baris 106–157) menunjukkan pembacaan state multi-kondisi: 

// Pembacaan state secara reaktif dari Provider
final productRepo = context.watch<ProductRepository>();
final products = productRepo.products;

// 1. Kondisi LOADING: Menampilkan spinner saat pertama kali fetch
if (productRepo.isLoading && products.isEmpty)
  const Center(
    child: CircularProgressIndicator(color: AppColors.primary),
  )

// 2. Kondisi EMPTY: Menampilkan visual kosong jika tidak ada produk
else if (products.isEmpty)
  Container(
    alignment: Alignment.center,
    child: Column(
      children: [
        Icon(Icons.inventory_2_outlined, size: 48),
        Text('Belum ada produk di kategori ini'),
      ],
    ),
  )

// 3. Kondisi SUCCESS: Merender grid produk aktif
else
  GridView.builder(
    itemCount: products.length,
    itemBuilder: (context, index) => FoodCard(product: products[index]),
  );

5.2 Implementasi Autentikasi & Exception Handling (LoginScreen)

Potongan kode dari lib/features/auth/screens/login_screen.dart (baris 72–195) menunjukkan siklus transisi dari Initial → Loading → Success atau Error: 

// 1. Transisi ke Status LOADING
setState(() => _isLoading = true);

try {
  // 2. Komunikasi ke Domain Service Layer
  final supabaseService = Provider.of<SupabaseService>(context, listen: false);
  final response = await supabaseService.signIn(email: email, password: password);

  // 3. Status SUCCESS: Umpan balik positif dan navigasi
  AppToast.show(context, title: 'Berhasil Masuk', type: ToastType.success);
  Navigator.pushReplacementNamed(context, '/home');
} catch (e) {
  // 4. Status ERROR: Penangkapan error dan umpan balik pengguna
  AppToast.show(
    context,
    title: 'Gagal Masuk',
    subtitle: 'Email atau kata sandi tidak sesuai. Silakan periksa kembali.',
    type: ToastType.error,
  );
} finally {
  // 5. Pemulihan status loading
  if (mounted) setState(() => _isLoading = false);
}
